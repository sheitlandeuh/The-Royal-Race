# The Royal Race — guide pour Claude Code

Jeu de courses hippiques (PC / mobile, navigateur), en français. Remplace l'ancien projet Turf Royal (abandonné).
Propriétaire : Enzo. Échanges et textes du jeu en français.

## Commandes
- `npm run build` : assemble `src/` en un seul `index.html` jouable (CSS et JS insérés, dans l'ordre alphabétique des fichiers ; chaque module dans une balise `<script type="text/x-module">`, exécutée par le chargeur final — voir Architecture).
- `npm run check` : vérifie seulement la syntaxe de chaque module et du bundle.
- `npm start` : build puis serveur local sur http://localhost:8000
- Sans Node : `python3 tools/build.py` (même résultat que `npm run build`, sans la vérification de syntaxe) puis `python3 -m http.server 8000`.
- `node tools/balance-test.cjs` : bot Playwright qui court des dizaines de courses (équilibrage).
- Sans installation : `tools/balance-bot.js`, à charger dans la console du jeu (`await import('./tools/balance-bot.js')`, puis `await bot.run([...])` ou `await bot.tactics('m2')`). Il couvre aussi les haies (politique `bot.smart.haie`).
- Tests : `await import('./tools/tests.js').then(m => m.run())` dans la console du jeu (`{quick:true}` pour la version rapide). À lancer avant chaque commit qui touche la course, l'équilibrage ou les premières minutes.
- En ligne de commande : `node tools/run-tests.cjs --quick` (Playwright, code de sortie 1 en cas d'échec). Intégration continue : `.github/workflows/verifications.yml` (bundle à jour, `check`, tests rapides, fumée PC + mobile) à chaque envoi sur `main` et `claude/**`.
- Test de fumée : `python3 -m http.server 8765` puis `node tools/smoke.cjs` (Playwright) — sept sauvegardes types (neuve → fin de partie, noms piégés, sauvegarde abîmée), tous les écrans ouverts, échec à la moindre erreur ou texte cassé (`ONLY=confirme` pour un profil, `--shots dossier` pour les captures PC et mobile). À lancer avant chaque commit : les erreurs de chargement n'apparaissent souvent qu'avec une partie avancée.
- Sans carte graphique (ou si Chrome a bloqué WebGL), le bot et les tests tournent avec une scène factice (`bot.headless()`). Ne jamais appeler `forceContextLoss` : Chrome bloque WebGL pour le site après plusieurs pertes de contexte provoquées.
- Ne jamais modifier `index.html` à la main : il est régénéré. On modifie `src/`, puis on build.

## Architecture
- Pas de framework, pas de bundler, pas de dépendance d'exécution. Three.js r160 (build global) dans `assets/vendor/three.min.js`.
- Chargement : un chargeur (fin de `index.html`) exécute les modules dans l'ordre au sein d'une seule tâche : aucune minuterie ne peut s'intercaler entre deux modules, une erreur n'empêche pas les suivants de démarrer (`window.__modulesKo`), puis il émet `ready`. Tout travail qui lit un module plus loin au démarrage se fait dans `hooks.on('ready',…)`.
- Événements (`hooks` dans `01-core`) : le moteur émet `ready`, `field:built`, `courses:render`, `race:start`, `race:header`, `race:go`, `race:launch`, `race:tick`, `race:steer`, `race:sprint`, `race:jump`, `race:end`, `race:leave`, `race:pace`, `moment:open`, `moment:choose`, `defi:end`, `duel:end`, `stable:render`, `tip` ; les modules V2 émettent `domaine:travaux`, `domaine:fini`, `domaine:recolte`, `vente:debut`, `vente:fin`, `legende`, `duel:partage`, `couronne`, `domaine3d:pret` (première image du domaine 3D), `fluidite` (qualité ajustée). Un nouveau module s'y abonne (`hooks.on`) au lieu de remplacer une fonction du moteur. Priorité facultative `hooks.on(e,f,p)` : tout ce qui modifie `racePlayer` au `race:start` doit passer avant l'enregistrement du rejeu (`p>0`, ex. jockeys `p=5`).
- `src/js/NN-nom.js` : modules en IIFE qui exposent un objet global (`stable`, `career`, `meta`, `season`, `breeding`, `rival`, `gear`, `tour`, `palmares`, `shop`, `HORSE3D`, `raceFX`, `domaine`, `ventes`, `legendes`, `duel`, `couronne`, `ecuries`, `fluidite`, `mesures`, `aide`…). `00-journal` s'exécute avant tout le reste (sans dépendance) pour attraper les erreurs de tous les modules (`journal`, `JOURNAL_ENVOI`). L'ordre des fichiers = l'ordre d'exécution : un module ne peut appeler un module plus loin qu'au moment de l'exécution (événements, rAF, `ready`), jamais au chargement (zone morte temporelle des `const`). Un module ajoute son écran avec `PANELS.nom = ouvrir` (`03-panels`), consulté par `openPanel`. Les données partagées entre modules se lisent dans `career.data` (ex. `legendes`, `ventes`, `couronne`) plutôt qu'en appelant un module chargé plus loin.
- Sauvegarde : `localStorage` — `trr.stable` (chevaux, casaque, ressources), `trr.progress` (carrière et tous les systèmes méta, dont `domaine`, `ventes`, `legendes`, `couronne`, `unlocks`), `trr.settings`, `trr.champion`, `trr.replays` (10 dernières courses), `trr.defi`, `trr.duels`, copie de secours `trr.bak`, journal local `trr.erreurs` / `trr.mesures` (rien n'est envoyé ; voir `docs/MESURES.md`). `sync()` enregistre automatiquement les ressources.
- Domaine (V2) : niveaux lus dès `01-core` (`domainLv`, `dlv(id)`), effets dans `DOMAIN_FX` (`dfx(id)`), `stableMax()`, `purseOf(meeting)` ; travaux, coûts et écrans dans `45-domaine`.
- Note d'un cheval : `ratingOf(stats)` / `stable.rating(h)` (pondération `RATING_W`, mesurée au bot). Les plateaux sont calés sur cette note : `ref = note + diff + FIELD_EDGE` (`12-stable-ui`). Toute nouvelle qualité ou tout nouveau talent se mesure au bot avant de toucher ces poids.
- Course : simulation déterministe à graine (`raceRng`, `seeded`), une étape toutes les 100 ms ; rendu Three.js séparé (`05-race-scene`, `09-race-fx`, `10-race`). Même formule de performance pour joueur et adversaires (`stable.racePerf` → `terrainPerf` → `gear.apply` pour le joueur). Temps forts (`27-moments`) : retirés en 2.4 (plan vide, aucune carte, aucune annonce) ; le module reste branché (`moments.fx`, entrée `moment`) pour réintroduire des décisions plus tard. Pendant la course, rien ne s'affiche par-dessus : `coach.tip` ne fait rien tant que l'écran de course est ouvert (le conseil n'est pas consommé), et le speaker (`43-speaker`) ne fait que parler tant que ton cheval n'est pas arrivé (texte seulement après l'arrivée). Rejeu (`36-replay`) : chaque course terminée est enregistrée (graine, plateau, paramètres du joueur après équipement et rythme, réaction au départ, programme des temps forts, actions datées au pas : `steer`, `sprint`, `pace`, `jump`, `moment`, toutes rejouées par `raceInput(type, val)` dans `10-race`) puis rejouée au retour au domaine ; `replays.verify(r)` doit rendre `ok:true` (option `{track:true}` : trajectoire pas à pas, utilisée par les duels). Toute nouvelle entrée du joueur qui influence la course doit passer par un événement enregistré, aucune formule de course ne doit lire l'horloge ni `Math.random`, et aucune ne doit lire l'écurie locale (`stable.active()`) : ce qui compte voyage dans `racePlayer` (ex. `racePlayer.tac`), sinon le rejeu d'un duel diverge sur l'appareil de l'ami. Temps forts : `MOMENT_FX` avec `dk` / `sk` (effet fonction de la distance). Moteur 4 (`ENGINE` dans `36-replay`, à incrémenter à chaque changement de formule — 4 depuis le rythme rééquilibré de la 2.4) — course pensée pour le multijoueur : départ commun sans bouton (`openGates`, à `RACE_GO_MS` après `startRace`, tirage des stalles `drawStalls` sur la graine), pas de pause (`raceClock` : le pas n tombe à GO + n × 100 ms, rattrapage si l'onglet dort ; aucun ralenti en direct ; conseils non bloquants en course), mêmes règles pour tous dans `runRaceV2` : couloir visé (`playerTarget` pour le joueur, `aiLane` pour l'IA), `lateral` (vitesse `LANE_V` × `agile`, arrêt contre un cheval à hauteur), `paceStep` (allure et énergie), `advance` (jamais à travers le cheval qui précède dans son couloir : `HORSE_LEN` × `HORSE_W`, allure plafonnée à la sienne × `check`), chevaux traités de la tête vers l'arrière. Invariant testé : deux chevaux en course ne se superposent jamais. `steer` ne déplace plus le cheval, il change le couloir visé ; ne jamais écrire `playerLane` directement (le bot fixe `playerTarget`). `racePerf` rend aussi `jump` (Départ, élan sur les 12 premiers %), `wideK` / `save` / `check` / `agile` / `draft` (Intelligence), `nerve` (Tempérament, via `crowdAt`), `jumpRisk` (haies) ; plateau calé sur `stable.ratingAt(h, dist)` (`RATING_D`), `FIELD_EDGE = 0`. Haies (`10-haies`, `RACE.haies`) : `haies.step()` appelé dans `runRaceV2`, choix du joueur `haies.choose` (entrée `jump` enregistrée), effets dans `HAIES_FX`. Le bot (`balance-bot`) déplace le cheval sans entrée enregistrée : ses courses ne se rejouent pas, les tests de rejeu pilotent `steer()` comme un joueur. Allure en course (2.5, `10-race`) : `setPace(v)` (-1 retenir, 0 normal, +1 presser ; entrée enregistrée `pace`, `playerPace` remis à 0 à chaque course), effets `PACE_IN` (vitesse × `c`, dépense × `d`, hors sprint final, joueur seulement ; ×1 exact à l'allure normale, donc moteur 4 inchangé), repère de réserve sur la jauge (1,2 × distance restante). Mesuré au bot (`bot.gestion`) : aucune allure fixe ne paie, lire sa jauge oui — test « Allure : lire sa jauge bat toute allure fixe » ; tout changement de `PACE_IN` se remesure ainsi. Rythme (`28-pace`) : tactique de chaque adversaire tirée à la création du plateau (graine), effets par rythme dans `PACE_FX`. Ambiances (`29-ambiance`, table `AMBIANCES`) : lumière, ciel, brouillard, pluie selon le terrain et l'heure. `30-photo` : mini-carte et arrivée serrée (effet d'image seulement, plus de ralenti depuis la 2.3). `31-heure` : lumière du village selon l'heure réelle (`?heure=nuit` pour tester).
- Affichage de la course (2.4) : `smoothRace` (appelé à chaque image) montre la course un pas en retard, interpolée entre `raceSnap` (état avant le dernier pas) et l'état courant, et pompe `raceClock` ; couloirs affichés `visualLane` sur ressort amorti, vitesse latérale `laneVel` (cap et inclinaison du cheval dans `raceFX.horse`, via `p.lat`). Tout ce qui dessine un cheval lit `visualProgress` / `visualLane`, jamais `playerLane` / `rivalLanes`. Affichage seulement : la simulation n'en dépend pas.
- Lumière : `raceFX.skyEnv(renderer, {zen, hor, gnd, sun, sunC, sunK, k})` rend une carte d'environnement PMREM (ciel en dégradé + soleil) ; course (`29-ambiance`) et domaine (`light()` de `51-domaine3d`) l'appliquent à `scene.environment` sauf en qualité basse, en baissant la lumière d'ambiance. Halo (bloom) dans le post-traitement de la course (`uBloom` selon la qualité).
- Chevaux 3D : `08-horse3d.js`, anatomie en surfaces implicites (SDF) maillée dans un Worker (surface nets en bande étroite ; repli sur le fil principal), `SkinnedMesh` sur 18 os (corps, encolure, tête, 3 os de queue, 4 jambes × 3), crinière posée sur la surface, queue en volume, jockey sur son propre squelette. Trois niveaux de détail (0 gros plan, 1 course, 2 domaine) : `HORSE3D.ready(lod)` puis `build(livrée,{number,blinkers,lod,free,seed})` rend un groupe qui s'assemble quand le maillage arrive (`userData.pending`) ; `pose(m,phase,allure,poussée,broute)`, `setLod`, `dispose`. En course, le modèle 3D sert sous tous les angles ; l'image peinte (`LIVERY.gallop`) ne sert que tant que le maillage se calcule.
- Monde de course : `09-race-world.js` (`raceWorld.build/update`, boîte à outils `raceWorld.kit` : fusion de géométries, arbres, feuillage au vent, drapeaux) ; densité selon `QUALITY`. Ombres : la zone du soleil suit la caméra (`09-race-fx`).
- Domaine (2.5 : **uniquement en 3D**, plus de peinture 2D, sur tous les appareils y compris en qualité basse) : `51-domaine3d.js` (`domaine3d.on/start/snap/view/quality/stats` ; chevaux de l'écurie au pré avec leur nom, décors `career.data.deco` achetés via `52-decors`, clavier). Coordonnées au sol en mètres (`B` = centre, hauteur de l'étiquette, orientation). `02-village` ne fait plus de rendu : il crée les étiquettes, minuteurs et boutons de chaque bâtiment dans le calque `#d3ui` (`village.layer`) et tient la sélection (`village.select/deselect`) ; `45-domaine` y ajoute les bulles de récolte (`data-id`) ; le domaine 3D les place par projection. Démarrage : `start()` construit l'essentiel (sol, bâtiments, clôtures), compile les shaders, affiche la première image (l'écran titre `splash` disparaît), puis ajoute décor, décors achetés et chevaux. Sans WebGL 2 ou si la construction échoue : `splash.fail` l'explique (le jeu entier a besoin de la 3D). Contexte WebGL perdu : message « Affichage 3D interrompu », reprise automatique quand le navigateur le rend. Ne jamais réintroduire de repli 2D.
- Domaine au repos (aucun geste depuis 1,2 s, caméra immobile) : 30 images/s au lieu de 60 (`geste` dans `51-domaine3d`). Chevaux 3D : `HORSE3D.dispose` libère aussi les squelettes (texture d'os) — test « Mémoire graphique stable entre les courses ».
- Vérifier sur capture sans attendre : `?heure=nuit|soir|matin|jour`, `?saison=hiver|printemps|ete|automne` (`31-heure` : `heure.phase`, `heure.season()`), `domaine3d.snap(ms)`. Le panneau du navigateur intégré, masqué, ne fait pas tourner `requestAnimationFrame` : forcer les images avec `domaine3d.snap`.

## Règles de travail
- Toute amélioration visuelle se vérifie sur captures réelles (Playwright + Chromium, 1280×800 et 390×844) avant d'être annoncée.
- Les changements d'équilibrage se vérifient avec le bot (taux de victoire attendu d'un bon joueur à la distance idéale ≈ 35–75 %). Tactiques : `bot.tactics('m2')` — la tactique choisie en lisant le plateau (« lecture ») doit battre chaque tactique fixe. Pour ces tests, simuler un joueur confirmé (`career.data.stats.races=10`), sinon le plateau débutant fausse tout.
- Aucun contenu factice visible par le joueur (boutons « bientôt », faux chiffres).
- Textes : temps avec `sec(x)` (« 89,55 s », virgule et espace insécable), espace insécable avant « : » dans les messages courts ; tout nom venu du joueur ou d'un lien (chevaux, duels) passe par `escapeHTML` ou `textContent` — profil de fumée « noms-pieges ». Petits écrans : l'écran de course se vérifie de 320 à 412 px de large (aucun chevauchement). Accessibilité : `REDUCE_MOTION` (réglage système) coupe animations CSS et secousse de caméra ; aucun texte sous 10 px. Sauvegarde impossible : `saveKo(e)` prévient le joueur une fois.
- Messages de commit en français, préfixés par la version (`v2.4 : …`).
- Style : `src/css/13-gaming.css` (chargée en dernier) porte l'habillage « gaming » (variables `--fd` titres Russo One, `--fu` interface Rajdhani, `--fb` texte Exo 2 ; néons `--neon` / `--neon2`, or `--gold`). Polices locales dans `assets/fonts` (OFL) : pas de police système « élégante » (Georgia) ni de police chargée depuis un CDN ; un nouveau composant reprend ces variables.

V2 livrée : domaine réel, ventes, Légendes, duels par lien (courses fantômes asynchrones sans serveur), La Couronne, équilibrage remesuré. 2.1 : chevaux, hippodrome et domaine en vraie 3D. Prochaine grande étape : comptes + sauvegarde cloud, économie validée côté serveur (le moteur de `replays.verify` tel quel), classement en ligne du Défi du jour et des duels, emballage stores (Capacitor) et achats intégrés.
